## 3. 아키텍처

### 3.1 모델 계보

`HybridANCNet` = Conv-TasNet 파형 encoder/decoder + WaveNet dilated causal TCN +
GCRN grouped LSTM. 원논문을 그대로 쓰지 못한 이유는 [README §2.3](../README.md#23-왜-원논문-구조를-그대로-쓰지-않는가)에 있다.

| 변형 | 파라미터 | C | 블록 | dilations | MHSA | 상태 |
|---|---:|---:|---:|---|---|---|
| `tiny` | 1.16M | 128 | 8 | 1,2,4,8 ×2 | — | **배포 후보** |
| `tiny_long` | 1.30M | 128 | 10 | 1,2,4,8,16 ×2 | — | 유의하지 않음 |
| `tiny_attn` | 1.23M | 128 | 8 | 1,2,4,8 ×2 | 4h | **실격** (do-no-harm) |
| `tiny_long_attn` | 1.37M | 128 | 10 | 1,2,4,8,16 ×2 | 4h | **실격** |
| `base` | 5.99M | 256 | **15** | 1,2,4,8,16 ×3 | 4h | 배포 탈락 |
| `tiny_wide` | **12.8M** | **512** | 8 | 1,2,4,8 ×2 | — | **지연만 측정** (미학습) |

### 3.2 end-to-end인 부분과 아닌 부분

**end-to-end** — 모델은 `(x_ref, err) → y`를 파형에서 파형으로 직접 매핑하고, 손실이
**에러 마이크 신호 자체**다. 미분 가능한 `S(z)`가 그래프 안에 있어 gradient가 `e`에서
가중치까지 흐른다.

```python
# losses/anc_loss.py:_forward_fp32
e = d + self.plant(y_nl, perturb)
```

**단계적(piecewise)** — 다음은 학습하지 않고 **측정해서 고정**한다.

| 요소 | 왜 고정하나 |
|---|---|
| `P(z)`, `S(z)` | 함께 학습하면 틀린 플랜트를 틀린 `y`로 벌충하고 **아무도 모른다** |
| `lead = 113` | 같은 이유 |
| 학습 단계 | Stage-1 합성 → **Stage-2 실측(진행 중)** → Stage-3 closed-loop. 각 단계 가정을 G1–G4로 검문 |
| 런타임 3스레드 | 마감 때문. 오프라인↔스트리밍 등가 `3e-8`이 분할이 수학을 바꾸지 않음을 보장 |

### 3.3 되먹임

에러 마이크는 **매 hop(2.67 ms) 모델 입력 ch1로 들어간다**.

```python
y = self.engine.step(ref, err)        # run_realtime.py
x = np.stack([ref, err])              # [1, 2, hop]
```

자기회귀(자기가 만든 `y`를 되먹임)와 다르다 — 후자는 `x_ref`로 이미 결정된 값이라 새
정보가 없고, 48 kHz에서 초당 48,000회 순차 forward가 필요해 예산을 26배 초과한다.

단, **현재 Stage-2는 `open_loop`**이라 모델이 "내 출력이 다음 `e`를 바꾼다"는 관계를 아직
학습하지 않는다. 그것은 Stage-3의 몫이다. 안전망은 `divergence_ratio 4.0 / hold 0.5 s`.

### 4.5 진단 — 용량 부족 (데이터 부족이 아니다)

| 구간 | train nmse_t |
|---|---:|
| 100–5,000 | −0.88 |
| 10,100–15,000 | −1.93 |
| 25,100–30,000 | **−2.46** |
| 35,100–40,000 | −1.50 |
| 45,100–50,000 | −2.07 |

**학습 NMSE 가 step 10,000 이후 −2 dB 에서 정체한다.** 이후 4만 step 동안 내려가지 않는다.
val 은 −0.07 dB 로 **train–val 격차가 2 dB 뿐**이다.

이것이 판별 근거다. 데이터가 부족하면 train 이 훨씬 더 내려가면서(예: −15 dB) val 만
나빠진다 — 과적합. 지금은 **train 자체가 막혔다**. 모델이 학습 데이터조차 맞추지 못한다.

`docs/12 §5.2` 판별표가 이 경우 **`tiny_wide` 용량 실험**을 지시하며, 그에 따라
`configs/train_pretrain_tiny_wide.yaml` 로 사전학습을 시작했다.

> 대안 설명을 배제하지는 않았다. 최적화 난이도, 손실 설계, 배치 16 의 gradient 잡음,
> 플랜트 모델 오차가 만드는 하한 등이 같은 증상을 낼 수 있다. `tiny_wide` 가 이 정체를
> 뚫지 못하면 용량 가설이 반증되고 그쪽을 봐야 한다.

### 4.6 추론 지연 — 30W vs MAXN

RT 우선순위 `chrt -f 80`, 코어 4–7 고정, warmup 500, 3000–5000 스텝.
**측정 환경에 데스크톱 세션이 떠 있어** 모든 조합의 max 가 40–58 ms 다 — 엔진 비교에는
쓰지 않는다.

| 모델 | 블록 | 엔진 | 30W P50 | **MAXN P50** | 30W P99 | **MAXN P99** |
|---|---:|---|---:|---:|---:|---:|
| `tiny` 1.16M | 8 | ORT CPU | 1.38 | **1.24** | 1.54 | **1.44** |
| `tiny` | 8 | TRT GPU | 0.56 | **0.29** | 3.27 | 3.12 |
| `tiny_wide` 12.8M | 8 | TRT GPU | 1.13 | **0.61** | 4.63 | **3.54** |
| `tiny_wide` | 8 | ORT CPU | 9.51 | 8.26 | 10.85 | 8.82 |
| `base` 5.99M | **15** | TRT GPU | 1.33 | **0.72** | 6.00 | **3.64** |
| `base` | 15 | ORT CPU | 6.00 | 6.01 | 6.40 | 6.40 |

**세 가지가 읽힌다.**

1. **MAXN 이 GPU P50 을 절반으로 줄인다** (tiny 0.56→0.29, wide 1.13→0.61, base 1.33→0.72).
   CPU 는 클록 상한이 27% 오른 만큼(~10%) 개선된다.
2. **폭은 GPU 에 거의 공짜, 깊이는 비싸다.** `tiny_wide` 는 `tiny` 보다 11배 큰데 GPU 에서
   2배만 느리고, 파라미터가 2.1배 많은 `base`(블록 15)보다도 **빠르다**. 비용을 내는 것은
   순차 커널 런치이지 연산량이 아니다.
3. **12.8M 모델은 GPU 에서만 실시간이 된다** — MAXN 에서 P99 3.54 ms < 예산 5.33 ms.
   CPU 는 중앙값 8.26 ms 로 예산을 넘는다.

TrtEngine 최적화 내역(30W 기준 P50 1.32 → 0.56 ms):

| 결함 | 고친 방식 |
|---|---|
| CUDA Graph 미사용 | parity 별 그래프 캡처 (H2D→추론→D2H 한 번에) |
| pageable 호스트 메모리 | `cudaHostAlloc` 고정 버퍼 |
| 매 스텝 `set_tensor_address` 26회 | A/B 두 경우를 그래프에 굳힘 |
| 동기 대기 정책 | `cudaDeviceScheduleSpin` |

그래프 경로는 비그래프 경로와 **비트 단위로 동일**하다(최대오차 `0.000e+00`).

### 4.7 실기 ANC (사전학습 tiny + ORT CPU)

| 시나리오 | 감쇠 |
|---|---:|
| tone 300 Hz | **+6.26 dB** |
| band (trusted) | **+5.14 dB** |
| 음성 + 소음 (80–800 Hz) | **+4.39 dB** |
| 1150–1250 Hz | +0.46 dB — 상쇄도 증폭도 안 함 |

## 5. 개선방안

### 5.1 지금 막고 있는 것 — 영향 순 (2026-08-05 파인튜닝 후 갱신)

| 순위 | 병목 | 근거 | 조치 | 자원 |
|---|---|---|---|---|
| 1 | **학습 NMSE 가 −2 dB 에서 정체** | §4.5 — train–val 격차 2 dB | `tiny_wide` 사전학습 **(진행 중)** | GPU 15h |
| 2 | **`music` 만 악화**(+0.58) — G4 를 막는 유일한 계열 | §4.4 | 원인 규명 후 데이터·손실 조치 | 분석 |
| 3 | `S(z)` 600 Hz 위 재현 불가 (0.74–0.84) | §2.3 | 상쇄 스피커·장착 개선 | **하드웨어** |
| 4 | I/O 왕복 30.4 ms = 루프의 **85%** | §1.3 | 블록 256 → 128 | 재측정·재학습 |
| 5 | `machine` 그룹 8개, val/test 각 1그룹 | §2.1 | G4 판정 신뢰도 — 녹음 보강 | 스피커 |
| 6 | 추론 지연 | §1.3 — 루프의 4.3% | (MAXN 전환 완료) | — |

> 순위 1·2 가 파인튜닝 결과로 새로 올라왔고, 이전 1순위였던 "실측에서 증폭"은
> **해결됐다**(+1.23 → −0.07 dB).

### 5.2 용량 가설 — 측정이 지시했고, 지금 검증 중이다

이전 판까지 이 절은 "용량이 병목이라는 증거가 없다"였다. **파인튜닝이 증거를 만들었다.**

**용량 부족을 지지하는 것 (§4.5)**

- 학습 NMSE 가 step 10,000 이후 **−2 dB 에서 정체**하고 4만 step 동안 내려가지 않는다
- val −0.07 dB 로 **train–val 격차가 2 dB 뿐**이다
- 데이터 부족이면 train 이 훨씬 더 내려가면서 val 만 나빠진다(과적합). 지금은 **train
  자체가 막혔다** — 모델이 학습 데이터조차 못 맞춘다

**여전히 배제하지 못한 대안**

| 대안 | 같은 증상을 낼 수 있는가 |
|---|---|
| 최적화 난이도 (lr·스케줄) | 가능 — `tiny_wide` 가 뚫지 못하면 여기를 본다 |
| 배치 16 의 gradient 잡음 | 가능 |
| 플랜트 모델 오차의 하한 | S 일관성 0.956 → 대략 −10 dB 근처가 한계이므로 −2 dB 를 설명하지 못함 |
| 손실 설계 (기능 2 를 평균으로 최적화) | 가능 — 최악값 목적함수 검토 필요 |

**과거에 큰 모델이 진 기록도 함께 본다**

| 비교 | 결과 |
|---|---|
| `base` 5.99M vs `tiny` 1.16M | 7종 소스 **전부** tiny 우세 |
| 최악 아이템 fullband | base **+13.89 dB 증폭** (do-no-harm 위반) |
| 구조 탐색 20k (4후보) | 어느 후보도 `tiny` 를 못 이김 |

단 이 기록은 **전부 surrogate 플랜트 + 합성 데이터**에서 나왔고, `base` 의 실패 양상은
용량 한계가 아니라 **과적합 신호**다. 실측 물리 + recorded 로는 한 번도 비교한 적이 없다.
그리고 그때의 탐색은 **깊이만** 바꿨다 — GPU 가 원하는 폭은 시험한 적이 없다.

**현재 실행 중**: `configs/train_pretrain_tiny_wide.yaml` (12.8M, C=512, 블록 8 유지).
tiny 와 다른 하이퍼파라미터는 하나도 바꾸지 않아 비교가 성립한다.

> **대가.** `tiny_wide` 는 MAXN GPU 에서 P99 3.54 ms 로 예산의 66% 를 쓴다
> (현재 `tiny`+CPU 는 27%). 여유가 줄면 OS 지터 흡수력이 떨어진다. 용량 이득이 그
> 위험을 살 만큼인지는 G4 비교로 판단한다.

### 5.3 순서

1. **`tiny_wide` 사전학습 100k** (진행 중, ~15시간) → 파인튜닝 50k → **G4 를 tiny 와 비교**
2. **`music` 악화 원인 규명** — 유일하게 나빠진 계열이고 G4 를 막는 단일 원인이다
3. G4 가 여전히 실패하면 §5.2 대안표대로 손실·최적화 쪽을 본다
4. 상쇄 스피커 개선 검토 — 기능 1 고역의 **유일한** 길
5. 블록 256 → 128 로 I/O 왕복 절반 시도 (Stage-3 closed-loop 대역폭에 직접 영향)
